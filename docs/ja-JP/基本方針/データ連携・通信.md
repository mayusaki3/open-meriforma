# Open MeriForma データ連携・通信 基本方針

## 1. 位置付け

Open MeriForma のデータ連携は、AI、シミュレーション、実機制御、Forma Unit、ログ、保守機能を分離しつつ、相互に連携できる構成を目指す。

上位AIやシミュレーションが実機の各関節を直接リアルタイム制御することを基本とせず、実機側の Main Controller が制御状態、安全性、身体構成を管理する。

通信方式やハードウェアを固定しすぎず、論理的な役割と物理的な通信経路を分離して設計する。

## 2. 全体構成

基本的なデータ連携構成を以下とする。

```text
AI Computer / PC / MuJoCo
        │
        │ Meridim / Management / Log 等
        ▼
MeriForma Main Controller
        │
        │ Forma Unit Protocol
        ▼
Forma Units
        │
        │ Device Native Protocol
        ▼
Actuator / Sensor / Driver
```

AI Computer、PC、MuJoCo、ログ保存等は論理的な役割として区別するが、必ずしも別々のハードウェアである必要はない。

小型PCやSBC上へ複数の役割を統合してもよく、必要に応じて外部PCへ分離してもよい。

## 3. 通信レイヤ

### 3.1 Meridim

Meridim は、PC、AI、シミュレーションと Main Controller 間で、機体全体の状態および制御指令を交換するために使用する。

Meridian Project のデジタルツイン思想を利用し、実機とMuJoCo等のシミュレーション環境を双方向に連携できる構成を目指す。

### 3.2 Forma Unit Protocol

Forma Unit Protocol は、Main Controller と各 Forma Unit 間の通信を担当する。

Meridimそのものを各ユニットまでそのまま延長することは前提とせず、Forma Unit に必要な識別、Capability、Health、アクチュエータ、センサー、保守等を扱える独立した通信層とする。

Meridim と Forma Unit Protocol 間は Main Controller で対応付ける。

### 3.3 Device Native Protocol

Forma Unit 内部では、実際に使用するデバイスに応じたネイティブ通信を使用できる。

例として、シリアルサーボ、PWMサーボ、モータードライバ、I2C/SPIセンサー等が考えられる。

外部の Forma Unit Protocol と内部デバイスの通信方式を分離し、デバイス固有仕様への依存をユニット内部へ閉じ込める。

## 4. Meridimを基準とした同期

Meridim の100Hz周期を、実機、シミュレーション、ログ等を関連付ける基本的な論理時間として使用する。

```text
Meridim Cycle = 0, 1, 2, ...
1 Cycle = 10 ms
```

Main Controller 内部では、これより高速な制御周期を使用できる。

基本案として、10,000Hz、100µs周期のベースTickを想定する。

```text
1 Meridim Cycle = 10 ms = 100 Control Ticks
1 Control Tick   = 100 µs
```

10kHz割り込みはスケジューラおよび時間基準として利用し、割り込み内で長時間処理を行わない。

1 Tick内で完了する必要のない処理は、状態機械等によって複数Tickへ分割して継続できるものとする。

壁時計時刻は、ログ表示等の補助情報として利用できるが、制御・同期の基本キーとはしない。

## 5. Real / Sim 間のデータ方向

データ連携では、Real と Sim / AI 間の方向を明確にする。

```text
Real → Sim / AI
  実測状態、センサー情報、機体状態

Sim / AI → Real
  目標値、行動要求、学習結果、制御指令
```

同じデータを両方向から同時に書き換えることを基本とせず、動作モードによって方向を決定する。

### 5.1 Real → Sim

実機状態を Meridim 経由でシミュレーションへ反映し、MuJoCo等のデジタルツインを実機へ同期できるようにする。

Real → Sim の通信が失われた場合でも、それだけを理由として実機を停止しない。

シミュレーション側では同期喪失を表示し、Real → Sim データを必要とする SysID 等の処理は中断または無効化できるものとする。

### 5.2 Sim → Real

Sim / AI から実機へ送られる指令は、Main Controller 側の安全判定を必ず通す。

```text
Sim / AI
   ↓
Meridim
   ↓
Main Controller
   ↓
Safety Check
   ↓
Real
```

安全制御範囲外の指令を受信した場合は、そのままアクチュエータへ伝達せず、停止処理へ移行する。

安全制御はSim / AIとは独立して実機側に存在する。

## 6. Meridim ID と Forma Unit

身体内の識別は Forma Unit を基本単位とする。

```text
Forma Unit ID
  └─ Local Device ID
      ├─ Actuator
      ├─ Sensor
      └─ Other Device
```

Unit ID は現在の機体構成における論理的な通信識別子として扱う。

Serial Number は物理的な個体を継続的に識別するために使用し、Unit IDとは分離する。

Health、SysID、部品交換履歴等は Serial Number と関連付けて管理できるようにする。

1つの Forma Unit が複数の Meridim ID に対応してもよい。

Meridim ID と Forma Unit内部のデバイスIDは直接同一とせず、Main Controller の対応表等によって関連付ける。

```text
Meridim ID
    ↓ mapping
Forma Unit ID + Local Device ID
    ↓
Native Device ID
```

Meridim ID が具体的に何を表すかは機体構成に応じてカスタマイズ可能とし、現段階では固定しない。

## 7. 多数アクチュエータへの対応

Meridimの1フレームで扱えるアクチュエータ数を超える構成では、複数グループを時間分割して扱うことを想定する。

例えば60軸の場合、Meridim自体の100Hz周期を維持しつつ、30軸ずつ交互に更新することで、各軸を実効50Hzで更新する構成が考えられる。

ただし、固定的な均等ラウンドロビン方式を規格として要求するものではない。

機体構成、重要度、制御要求等に応じて、Meridim IDの割当や更新スケジュールを変更できるものとする。

Main Controller 内部のアクチュエータ状態は Meridim の更新周期とは独立して保持する。

## 8. AI・認識データ

画像や音声等の生データを Meridim に格納することは基本としない。

カメラ、マイク等の大容量データはAI Computer側で処理し、Main Controllerへは認識結果や行動に必要な情報を送る。

```text
Camera / Mic
    ↓
AI Computer
    ├─ Vision
    ├─ ASR
    ├─ Tracking
    └─ Recognition
        ↓
Recognition / World State / Intent
        ↓
Main Controller
```

概念的に以下を区別する。

```text
Meridim    = Physical State
Perception = World State
Behavior   = Intent
```

認識結果を実機状態と関連付ける場合は、可能な範囲で元データ取得時の Meridim Cycle を保持する。

## 9. SysID とデジタルツイン

SysIDは、アクチュエータ単体だけではなく、実際に組み込まれた機構全体の特性を対象とする。

```text
Command
  ↓
Actuator
  ↓
Transmission / Gear / Differential
  ↓
Joint
  ↓
Load / Friction / Elasticity
  ↓
Measured Joint State
```

Open MeriFormaでは、アクチュエータ、伝達機構、関節、センサー、実装状態を含めた Assembly SysID を重視する。

SysID結果は、制御パラメータ、MuJoCoデジタルツイン、Health評価等へ利用できるものとする。

初期状態、現在状態、過去のSysID履歴を区別して保持し、再学習によって劣化や特性変化の履歴を失わないようにする。

## 10. 通信異常時の基本動作

### 10.1 Sim / AI → Main Controller の通信断

Sim / AI から Main Controller への通信が失われた場合は停止処理へ移行する。

ただし、すべての状態で単純に即時脱力することを基本とはせず、現在の動作状態に応じた安全な停止シーケンスを使用する。

歩行中、倒立振子移動中、着座中、上肢動作中等の具体的な停止方法は、各機構・制御設計時に定義する。

### 10.2 Main Controller → Forma Unit の通信断

Main Controller と Forma Unit 間の通信断は故障として扱う。

対象ユニットは基本的に駆動力を解除する方向とし、利用不能な Capability として扱う。

Main Controller 自体が正常であり、残存する身体能力で安全に動作可能な場合は、故障ユニットを除外して継続動作できるものとする。

通信が完全に失われた状態ではMain Controllerからの脱力指令自体が到達しない可能性があるため、具体設計ではユニット側のWatchdog等を含むFail-safeを検討する。

### 10.3 Forma Unit 内部のデバイス故障

可能な場合はデバイス単位で故障を管理し、Forma Unit全体を即座に無効化することを要求しない。

故障したデバイスに依存するCapabilityを無効化または制限し、残存機能を利用できる構成を目指す。

危険な状態ではユニット側でも安全停止できるものとする。

### 10.4 通信遅延・部分欠落

安全に影響する一定時間以上の遅延または欠落は、完全な通信断と同様に扱う。

TimeoutはMeridim Cycle等の論理時間を基準として定義する。

具体的なCycle数は実機設計時に決定する。

## 11. データFreshness

Meridimに個別データの「今回未更新」を明示する規約がない限り、個別IDごとのFreshness監視は必須としない。

基本的には通信経路・フレーム単位で更新状況を監視し、一定Cycle以上有効なフレームを受信できなかった場合に通信断と判断する。

多数アクチュエータを時間分割して更新する場合、更新対象外であった値を単純にStaleとは扱わない。

将来Meridim側に個別データの有効性や更新有無を示す仕組みが追加された場合は、個別Freshness管理を再検討する。

## 12. バージョン管理とファームウェア更新

Main Controller と Forma Unit の Runtime Protocol は、対応するバージョンの一致を要求する。

バージョンが一致しない場合、その Forma Unit の通常動作を許可しない。

互換層を複雑に維持することより、対応するファームウェアへ更新してバージョンを揃えることを基本とする。

将来的には、通常通信経路を利用して Main Controller または上位PCから Forma Unit のファームウェアを更新できる構成を目指す。

バージョン不一致時でも更新を可能にするため、通常制御とは分離した最小限の保守通信機能を持たせることを検討する。

保守通信で扱う候補は以下とする。

- Unit識別
- Runtime Protocol Version取得
- Firmware Version取得
- Firmware Update
- Reboot
- 最低限の診断

この保守通信仕様は可能な限り小さく安定させ、Runtime Protocol の更新から独立して使用できるようにする。

## 13. ログ

### 13.1 Main Controller 内部ログ

Main Controller は、メモリ内にリングバッファ形式でログを保持できるものとする。

通常は古いデータを上書きしながら保持し、必要時にWiFi等の通信経路からログ表示・取得コマンドによって読み出せる構成を想定する。

安全停止や故障等のイベント発生時に、直前の履歴を保持できる仕組みを検討する。

### 13.2 WiFiによるログ出力

WiFi接続中は、Main Controller からログをリアルタイム出力し、接続先のPC等で保存できる構成を想定する。

Real → Sim の通信と同じWiFi経路を併用可能とする。

Real → Sim で既に送信している Meridim データは、PC側でDigital Twin入力とログ保存へ分岐できるため、ログのためだけに同一データを重複送信することを要求しない。

Meridimに含まれないDebug、Health、Forma Unit診断、SysID追加情報等は別の論理ログとして送信できるものとする。

ログ通信はRealtime通信より低優先度とし、ログ出力によってMeridimや制御通信を阻害しない。

通信帯域不足時はログを欠落させても制御通信を優先する。

## 14. 上位ネットワーク通信

Main Controller は実機側の通信ハブとして動作する。

AI Computer、PC、MuJoCo等との接続は、Meridianとの親和性と取り回しを考慮し、WiFi/IP通信を中心に検討する。

同一の物理通信経路上で、用途を論理的に分離する。

例:

```text
Realtime Channel
  - Meridim

Management Channel
  - Unit情報
  - Version
  - 設定
  - Firmware Update

Log Channel
  - Monitor
  - Record
  - Debug
```

将来USB、Ethernet等の物理通信を追加しても、上位の論理プロトコルや役割を大きく変更しなくて済む構成を目指す。

## 15. Forma Unit 間の物理通信

Main Controller と Forma Unit 間の具体的な物理通信方式は、実機設計段階で決定する。

現段階では以下を基本的な検討条件とする。

- 複数 Forma Unit を接続可能であること
- 身体内配線として扱いやすいこと
- ノイズ耐性を持つこと
- 必要なリアルタイム性を確保できること
- 低コストかつ個人製作しやすいこと
- 必要に応じて複数バスへ分割可能であること

CAN / CAN-FD、RS-485等を候補とするが、この基本方針では採用方式を確定しない。

通信バス故障時の安全性を確保するため、必要に応じて通信とは独立したSafety / Enable信号やユニット側Fail-safeを検討する。

コネクタ、信号数、電源電圧、バス構成、終端方法等は実機設計で決定する。

## 16. 今後の実機設計で決定する事項

以下は本基本方針では固定せず、実機設計・試作・検証を通じて決定する。

- Main Controller の具体的なMCU
- AI Computer / SBCの具体的構成
- Forma Unit Bus の物理方式
- CAN / CAN-FD / RS-485等の選定
- コネクタおよびピン配置
- 電源電圧
- Forma Unit Protocol の具体的なフレーム形式
- Capabilityの具体的なデータ構造
- Meridim ID と Forma Unit の具体的なMapping
- 多数アクチュエータ時の具体的な更新スケジュール
- 通信Timeout Cycle数
- 状態別の安全停止シーケンス
- SysIDの具体的なアルゴリズムおよびパラメータ形式
- ログフォーマットおよび保存容量
- Firmware Update方式

## 17. 全体思想

Open MeriForma のデータ連携では、AI、シミュレーション、実機リアルタイム制御、安全制御、身体モジュール、ログ・保守を分離し、それぞれの責務を明確にする。

実機状態は Real → Sim / AI、目標・意図・制御指令は Sim / AI → Real を基本方向とし、Sim → Real の指令は必ず実機側安全制御を通す。

Meridimを実機全体とデジタルツインを結ぶ上位同期層、Forma Unit Protocolを交換可能な身体モジュールを結ぶ身体内通信層、Device Native Protocolを個別デバイス層として扱う。

通信やログ、AI処理の障害が安全制御を無効化しない構成とし、身体構成の変更、部品交換、故障、経年変化へ対応できるPhysical AIプラットフォームを目指す。
